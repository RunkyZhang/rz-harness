# 领域名词：哪些保留、哪些可改

> 日期：2026-08-29  
> 用途：自建 harness 时的用词。保留的是为了和 Cursor / 标本 / 以后的 superpowers、ECC 对得上；可改的是标本自己的实现名，不必当行业标准背。  
> 相关：[04-由浅入深学习路径-从0按标本写harness.md](04-由浅入深学习路径-从0按标本写harness.md)  
> 每个词为什么用、用来做什么：见 [06-领域名词总表-为什么用这个词用来做什么.md](06-领域名词总表-为什么用这个词用来做什么.md)

总原则：

1. **运行时认的文件名和目录名不要改**（它找不到就不加载）。
2. **给人看的正文用中文**；代码、脚本、YAML key、错误码继续用英文（标本这条语言政策值得留）。
3. **机制留、商标式名字可换。** 换名时选「一听就知道在查什么」的词，方便以后写 gate。

---

## 必须保留（生态 / 工具会按这个词找）

这些不是品味问题，改了会和 Cursor、Codex、开源文档对不上。

| 词 | 为什么必须留 |
|---|---|
| `AGENTS.md` | 各 runtime 的约定入口，不要改成 `规则.md` |
| `SKILL.md`、skills 目录 | Cursor / Claude / Codex 的 skill 包装就是这个文件名 |
| hook、`.cursor/hooks.json` | 工具配置字面量 |
| worktree | Git 命令和文档原文 |
| eval | 评测圈通用；以后读 ECC/superpowers 都是这个词 |

**harness** 建议留作类别名（「这是控制面 harness」），不必写进每个文件名。仓库可以叫你自己的名字，不必叫 `xxx-harness`。

---

## 建议保留（不是硬约定，但改了交流成本高）

和 CI、Fowler、标本、以后两套开源教材是同一套词。学习阶段用英文，对人解释时可以跟中文。

| 词 | 对人可以说 | 建议 |
|---|---|---|
| **gate** | 关卡、门禁 | **留。** 脚本继续 `*-gate.sh`。这是 CI 里的质量门，不是标本发明。 |
| spec | 规格 | 留 `spec.md` |
| review | 审查 | 留 `review.md` |
| evidence | 证据 | 文件名可留 `evidence.md`，标题用中文「证据」 |
| adapter | 适配 | 文档里中文「薄适配」；目录 `hooks/` 即可 |
| subagent | 子 Agent | 留，Cursor 就这么叫 |
| TDD、fail-closed | 测试先行、说不清就失败 | 留英文缩写没问题 |
| baseline | 基线 | 仓说明用中文「基线」，文件名 `baseline` 也可 |
| `allowed_paths` | 允许修改的路径 | YAML key 留英文，和标本 gate 对照方便 |

**lane**：可留文件夹 `lanes/`（短）。对人说「任务路线」，不要说「请走 lane」。

**`[FACT]` / `[ASSUMP]` / `[QUESTION]`**：不是行业标准写法，但**建议留这套标签**。短、能 grep、标本第一个 gate 就是按它们扫的。对人说话用「事实 / 假设 / 问题」。不要改成一长句中文标签，gate 会变脆。

---

## 可以改（标本实现名，换成更直白的更好）

机制要学，名字不必克隆。

| 标本叫法 | 它实际是什么 | 自建更直白的叫法 |
|---|---|---|
| `confidence-gate` | spec 里还有未决问题/假设就不准往下 | `spec-gate` 或 `questions-gate`（查什么就叫什么） |
| `assumption-leak-gate` | 实现文件里漏进了未确认假设 | `no-assumptions-in-code.sh` 或 `assumption-in-code-gate` |
| `harness-status.md` | 给人看的进度单 | **`status.md`**。卡片、状态卡当中文别名 |
| Optional Pack | 默认不加载的附加流程 | **附加流程** / `addons/`，不必叫 Pack |
| Tier S/M/L | 小 / 中 / 大 工作量档 | 文档写 **轻 / 中 / 重**；若需要 id 用 `s` `m` `l` 即可 |
| Test Agent + `GOAL_ACHIEVED` | 独立验收角色 + 通过态 | 角色叫 **验收**；状态用 `PASS` / `BLOCKED`（少戏剧性） |
| `skill-usage.md` | 强制填写的 skill 台账 | v0 **不要这个文件**。以后用事件日志，不要叫 usage gate |
| Orchestrator | 主会话、控制面可写 | v0 叫 **主 Agent**。真有多角色再引入 Orchestrator |
| change-id / 变更包 | 一次工作的文件夹 | 文件夹可留 `changes/<id>/`（清楚）；对人说「这次工作」即可 |
| Guides / Sensors | Fowler 的规则 vs 检查 | 写进学习笔记没问题；**不要**写进给你自己看的 `AGENTS.md`。用「规则」和「检查脚本」 |
| control plane | 控制面 | 中文 **控制面** 即可，不必中英叠说 |
| code-start | 第一次改业务代码前的总检 | 对人说 **开工检查**；脚本名 `code-start-gate.sh` 仍可认 |
| `GOAL_ACHIEVED`、`high_risk_count` | 验收/审查合同字段 | 可留作 YAML 字段（机器读），或改成 `status: pass` + `high_risk: 0` |

**confidence** 尤其建议改：它不像「在查什么」，像一句口号（95% 把握）。你自己的第一个 gate 按学习路径是检查 spec 问题清没清，叫 `spec-gate` 更贴。

---

## 不要当领域名词去学的（业务积木，不是 harness 词）

SFA、mapSystem、Feishu sync、Swagger VO、product group 登录……这些是标本服务的产品。自建不要进词表。

---

## 写 v0 时的用词约定（可直接当规范）

**文件 / 脚本（英文，短、能 grep）**

- `AGENTS.md`
- `changes/<id>/spec.md`
- `changes/<id>/status.md`（不必 harness-status）
- `changes/<id>/evidence.md`
- `changes/<id>/review.md`
- `scripts/spec-gate.sh`（对应标本 confidence-gate）
- `scripts/allowed-paths.sh`
- `skills/reviewer/SKILL.md`
- `lanes/tiny.md`

**对人（中文）**

- 关卡 / 门禁 = gate
- 状态卡 = status.md
- 变更包 = changes/<id>/
- 任务路线 = lane
- 规则 vs 检查脚本 = 不必出现 Guides/Sensors
- 主 Agent / 只读审查 = 不必先上 Orchestrator

学习标本时：脑子里做一次翻译——看到 `confidence-gate` 就映射到你的 `spec-gate`，不要并存两套口头禅。
