RZ AI Harness 使用手册

给人看的操作手册：你（人类）在每一步要做什么、要提供什么、在哪里停下确认。设计与机制说明见 readme.html；Agent 规则见仓库根目录 AGENTS.md。

目录 0. 开始前准备 1. 整体流程 2. 发需求 3. 需求理解 4. 方案与测试方案 5. 实现与 UI 6. Tester 与报告 7. Reviewer 与人审 8. 收口 9. 常见问题

0. 开始前准备

工作区

  • Cursor：先打开 rz-harness，再用 File → Add Folder to Workspace 把本次要改的业务仓（如 sfa-backend）加进来。工作区设为 Trusted。
  • OpenCode：从 rz-harness 启动即可；它可以直接访问业务仓的绝对路径。
  • 不要把业务仓 clone 或拷进 rz-harness。业务代码始终用磁盘路径引用。

你要准备的资料

  • PRD：文件、飞书链接或正文。
  • 目标仓：本次改哪个/哪些 repo_id（如 sfa-backend）。
  • 档位：S / M / L；不确定就让 runtime 判断。
  • 范围：是否涉及 UI、DB、飞书 PRD、跨仓、导出/分析。
  • 环境：本地/测试/预发；账号来源；是否允许写库（默认只读）。
  • 业务仓状态：如果有未提交改动，提前说明。

1. 整体流程

你只需要在下面这些人参与的点停下来；其余门禁、实现、Tester、Reviewer 由 runtime 自动执行。

人类动作速查

时机你要做什么怎么回复
需求理解答阻塞 [QUESTION]，确认/推翻 [ASSUMP]直接回答问题；不确定就说“按 A 方案”
技术方案（M/L）审方案“确认方案”或提出修改
AI 测试方案（M/L）审测试方案“确认测试方案”
复杂 UI（条件）看可运行页面 / 截图“UI 确认”
AI 测试报告审报告、残余风险、是否进预发“确认报告”（进预发再加“允许进入预发”）
最后人工 review / PR / SIT—

2. 发需求

第一条消息建议一次给全，别只丢一句“做个 XX”。

需求：<一句话>
PRD：<文件路径 / 飞书链接 / 正文>
目标仓：<repo_id，如 sfa-backend>
档位：<S/M/L 或 让你判断>
范围：<后端接口 / 是否含 UI / 是否改 DB / 是否跨仓>
环境：<本地 / 测试 / 预发；账号来源；是否允许写库>
备注：<已知限制、不能改的模块、参考实现>

runtime 会先建 changes/<change-id>/、写 spec.md，然后停下来问你。

3. 需求理解（你答）

runtime 会列出 [FACT] / [ASSUMP] / [QUESTION]，并给出本次会碰到的关卡。

  • 回答所有阻塞 [QUESTION]；
  • 确认或推翻 [ASSUMP]；
  • 不确定的就说“不确定，按 A 方案 / 先不做”。
阻塞问题没答完，runtime 不能写业务代码。你答完后它会原地改成带来源的 [FACT]，再跑 confidence-gate.sh。

进度看 changes/<change-id>/status-card.md（状态卡），那是给人看的单一入口。

4. 方案与测试方案（你确认）

M/L 档会停两次：

  1. runtime 给 technical-solution.md（全栈方案）→ 你回复「确认方案」或提修改。
  2. Test Strategy 给 ai-test-plan.md（测试方案）→ 你回复「确认测试方案」。

S 档这两步通常 N/A，不会停。

你不需要改 YAML。口头确认后，runtime 会把确认状态写进对应文件，再跑 gate。

5. 实现与 UI

runtime 会：切 harness/<change-id> 分支（不在 master 改）、跑开工门禁、改 allowed_paths 内的代码、记 evidence.md、跑编译/单测/静态检查。

你要做：

  • 需要登录 / 写库 / 起服务时提供信息；
  • 涉及 UI 时，页面可运行后你会被要求看页面确认；
  • 不要手动改 spec.md / contract.md（会让 gate 失真）。

6. Tester 与测试报告

  • Tester（独立角色）验收，写 test-agent-verification.md；只有 GOAL_ACHIEVED 才放行，BLOCKED 会升级给你。
  • 提测 / 预发前，runtime 给 ai-test-report.md → 你回复「确认报告」；进预发还要确认「允许进入预发」。

7. Reviewer 与人审

  • Reviewer 只读审查，要求 high_risk_count: 0。
  • 然后你人工 review / PR / SIT。

8. 收口

  • 有踩坑 → 按模板写 docs/pitfalls/RZ-PIT-*.md；
  • 有决策 → decisions.md（L 档）；
  • retro 复盘。

9. 常见问题

只开了 rz-harness 工作区，runtime 改不了业务仓？

Cursor 用多根工作区（Add Folder to Workspace）把业务仓加进来；OpenCode 从 rz-harness 启动即可用绝对路径访问。

口头说“ok”能跳过确认吗？

不能。方案、测试方案、报告需要明确确认，gate 会拦。

环境没准备好会怎样？

依赖 Nacos / DB / 账号的步骤会 BLOCKED，这不算代码失败。准备好后继续。

我可以自己改 spec / contract / evidence 吗？

不建议。让 runtime 改，否则 gate 结果会失真。

业务仓有未提交改动怎么办？

提前告诉 runtime；它会先写 dirty-worktree-ledger.md，避免覆盖你的工作。

status-card 是什么？

changes/<change-id>/status-card.md 是给人看的单一进度入口：走到哪、下一步、卡在哪、要不要你拍板。只有主 Agent 写。
