RZ AI Harness 说明

给人看的控制面说明书。内容整理自仓库根目录 AGENTS.md。Agent 执行时仍以 AGENTS.md 为准；两边若有出入，先改 AGENTS.md，再改本页。

这是什么

本仓库 rz-harness 是 RZ AI Harness 的控制面：规矩、模版、gate、子 Agent 人设、变更包工作目录。业务代码在各自的 git 仓里，用磁盘路径引用，不要把业务仓 clone 或拷进本目录。

runtime 是真正跑起来的程序（Cursor / Codex / OpenCode），负责读文件、跑命令、权限和沙箱。harness 套在 runtime 外面，规定改哪些文件、什么时候必须停、宣称完成要拿出什么证明。

目录怎么分

类含义放哪
配置类按本机环境和所用 runtime 填写要每人填写、且不进 git 的，是 config/runtime_local.sh（仓的绝对路径、端口、凭据来源）以及各 runtime 自己的接线文件（.cursor/hooks.json、.codex/hooks.json、OpenCode plugin）。仓名单 git-registry.md 和 hooks/ 里的检查脚本是全员同一份，要进 git。
静态类装好即用，不按机器改语言政策、templates/、gates/、scripts/、skills/、子 Agent、baselines/、rules/、本页所在的 docs/

本机要填的

  • 复制 config/runtime_local.example.sh 为 config/runtime_local.sh。至少填：业务仓绝对路径、账号/凭据来源、数据库连接信息、本地服务地址/代理/端口、本机工具命令。
  • 明文密码、token、cookie 只放在这个文件或系统钥匙串。禁止写入 spec、evidence、状态卡或任何会进 git 的文件。

语言

给人工 review 和用户确认的文档用简体中文。代码标识、命令、API 路径、字段名、错误码、YAML key、日志 key 保持原文。

Git 仓库

名单以 git-registry.md 为准。登记表写仓名和变量名（如 $RZ_REPO_SFA_IOS）；每人本机路径写在 config/runtime_local.sh。当前范围：

  • 后端：sfa-sales-management、sfa-backend、sfa-root、sfa-base、arch-open、arch-event、sfa-common-sdk
  • Web：mapSystem
  • App：sign-up、sfa-ios、sfa-android

按需打开的字典

  • 仓说明书：baselines/。只读本次改到的仓。写 allowed_paths、选样板、第一次改业务代码之前要读。Reviewer 审查该仓 diff 时对照分层、样板和受保护路径。mapSystem 还要遵守 baselines/frontend-map-system.md 的 Node 版本、登录和临时路由。
  • 模版：templates/，字典 templates/template_directory.md
  • 门禁：gates/，字典 gates/gate_directory.md
  • 脚本：scripts/，字典 scripts/script_directory.md
  • skill：skills/，字典 skills/skill_directory.md
  • 给人看的文档：docs/。给模型生成代码时参考的规则：rules/

Hook

Hook 是 runtime 的功能：到了某个事件点，runtime 一定会去跑脚本，不靠模型记得。Gate 是检查内容；hook 是触发时机。接线按 hooks/hook_setup.md。本仓不提交各 runtime 的接线文件。

领域名词

档位

档位看的是改动范围、风险和环境依赖，不看功能点多少。改权限或动真实库可以是 L；页面很多的单仓低风险小修可以是 S。

档典型样子流程上多什么
S单仓小修、文档、低风险脚本spec、状态卡、证据
M普通全栈或多文件业务，大约 1～2 个 API在 S 上再加强制方案、契约、测试方案、Tester、Reviewer
L跨仓、高风险、强依赖真实环境、发布前风险高在 M 上再加环境就绪、测试报告、决策记录

S 档这些默认可写 N/A 和原因：契约、技术方案、AI 测试方案、plan 与 verification-map、Tester、AI 测试报告。spec、allowed_paths、evidence 仍然要有。

需求理解：FACT / ASSUMP / QUESTION

主 Agent 把「PRD 写了的 / 代码里已有的 / 用户说的 / 模型猜的」拆开，写进 changes/<change-id>/spec.md。聊天不是事实源。没出处的业务规则、字段、状态、权限、错误码、默认值、回滚规则不是事实。拿不准时写成 [QUESTION]。

标签是什么限制
[FACT]有出处：PRD、用户确认、现有代码、已冻契约、线上已有行为只有这类可以进实现
[ASSUMP]模型推断、尚未确认不挡开工，但不得作为实现依据。渗进实现文件时 gates/assumption-leak-gate.sh 会 FAIL
[QUESTION]必须用户决定，Agent 不能代选阻塞项未清，不得写业务代码
  • 三种标签都必须出现。没有假设就写 [ASSUMP] None.
  • 不影响本次实现的问题放到 non_blocking_questions:，默认不拦开工。吃不准是否阻塞，就放正文当阻塞项。
  • 建包时模板里的标签只是占位，不是已经问过用户。需求理解阶段写实质内容，然后停下来问。用户答完，主 Agent 原地把该行改成带来源的 [FACT]，再跑 gates/confidence-gate.sh。口头「ok」不算过。
  • 契约、技术方案模板里的 [QUESTION] 只是空格，confidence-gate 不扫那些文件。
  • Explorer 可选、只读、不改 spec.md。它在对话里按三标签供料。主 Agent 决定采纳后再落文件。
Gate查什么不过意味着
gates/confidence-gate.sh阻塞 [QUESTION] 是否还在；lane 是否为唯一合法值，且与状态卡 Lane 一致问题没答完，或 lane 仍是 TODO / 与状态卡不一致，不能开工。未确认的 [ASSUMP] 本身不挡开工
gates/assumption-leak-gate.sh实现文件里有没有 [ASSUMP] 字面标签，以及 spec 里假设的标识符有没有漏进实现假设漏进实现

Guides 与 Sensors

Harness 围住 Agent：行动前喂资料（Guides），行动后压检查（Sensors）。Guides 靠读起作用，本身不拦截。模型可能不读，或读了仍违反，所以要有 Sensors。需要人拍板的节点是停止点：循环暂停，把控制权交回给人。

gate

  • 位置 gates/，字典 gates/gate_directory.md。bash 脚本。exit code 0 是 PASS，非 0 是 FAIL。
  • FAIL 输出四要素：FAIL / CODE / FIX / SAMPLE（问题、错误码、怎么修、参考）。
  • gate 只裁决，不干活。检查对象是 changes/<change-id>/ 下的产物。命令痕迹记在 evidence，不由 gate 承载。

停止点

停止点和下面 15 个步骤的编号不是一一对应。停止点分两类：用户拍板（口头确认后由主 Agent 写入对应文件，再跑 gate，用户不用改 YAML）；自动关卡或独立角色（gate、Tester、Reviewer）。BLOCKED 是合法停、升级给人，不是放行。状态卡只镜像进度，不是拍板原文。

用户平时要做的：答 QUESTION（1）→ 确认方案（2）→ 确认测试方案（3）→ 条件触发时确认 UI（6）→ 确认测试报告（8）→ 人工 review。4 / 5 / 7 / 9 平时不用逐项参与。

环境材料可以提前准备，强制时点在真实 E2E 之前。Code start 先于 E2E。验收阶段可以同时挂 Tester、测试报告、Reviewer。契约冻结不在这 9 个编号里，未冻不得实现。真实库写入的二次确认挂在实现阶段，仍由用户拍板。合并前卫生扫描是检查项，不是决策停止点。

整体工作流

这 15 步是索引。有匹配的 lane 时，步骤菜单用那份 lane，这 15 步用来核对停止点有没有被跳过。没有匹配则 lane: none，用这 15 步，再按档位裁剪。门禁细节见停止点和强制工作流，产物见文件列表。未命中的步骤写 N/A 和原因。
普通步骤 要人确认 自动关卡 Tester Reviewer
  1. 定 change-id：用业务含义命名。
  2. 选 lane：见下一节。有匹配时步骤菜单用该 lane。
  3. 建变更包：changes/change-scaffold.sh --tier S|M|L <change-id>。建包后把 spec 文首 lane: TODO 改成唯一合法值，状态卡 Lane 照抄。同时写入阶段、下一步、阻塞。
  4. 写 spec：用户确认的写 FACT，推断写 ASSUMP，需拍板写 QUESTION，并写 allowed_paths。写完停下来问。答完后原地改成带来源的 FACT，再跑 confidence-gate。口头 ok 不算过。（停止点 1）
  5. 冻结契约：changes/<change-id>/contract.md。S 或无 API 可 N/A。未冻不得实现。
  6. 技术方案（M/L）：technical-solution.md 加用户确认。（停止点 2）
  7. AI 测试方案（M/L）：独立 Test Strategy 写 ai-test-plan.md。主 Agent 不得代写。用户确认后，主 Agent 写成 test_plan_status: CONFIRMED。（停止点 3）
  8. plan 与 verification-map（M/L）：方案确认后、开工前填写。S 可 N/A。
  9. 开工门禁：从远程主干拉 harness/<change-id>。S 三重，M/L 四重。不在主干上改。（停止点 5）
  10. 实现 + 记证据：只改 allowed_paths 内文件，命令记入 evidence。PRD 有界面时，写代码前先写 ui-rule-checklist.md，规则缺口停下等用户。（停止点 6）
    • 常规验证（进入 Tester 前）：编译、定向测试、窄范围 lint。前端用 scripts/frontend-lint-build.sh 的 lint-files，后端用 scripts/mvn-targeted-test.sh。verification-map.md 有可执行行时跑 scripts/verification-run.sh。跑不了写 BLOCKED 和原因。已选 lane 时以该 lane 的验证命令为准。S 档没有 Tester 时，这项改在 Reviewer 之前完成。
    • 复杂 UI：页面可运行后写 ui-confirmation.md，用户看过再确认。
    • Optional Pack：E2E 按 lanes/pc-e2e-smoke.md。Impact / Parallel（CodeGraph、GitNexus、多 Agent worktree）本仓未引入，写 N/A。
  11. Tester 验收（M/L）：Tester 填写 test-agent-verification.md。主 Agent 不得代填、不得自称 GOAL_ACHIEVED。未达到则回到第 10 步。BLOCKED 升级给用户。（停止点 7）
  12. AI 测试报告（提测 / 预发）：ai-test-report.md 加用户确认。（停止点 8）
  13. Reviewer 过门：只读审查，high_risk_count: 0。S 走 bugfix-fast 时仍建议 Reviewer。（停止点 9）审查前跑 scripts/code-comment-log-quality.sh。
  14. 人工 review / PR / SIT。合并前卫生扫描见受保护行为。
  15. retro 收口。

lane

lane 是某类任务的默认步骤清单，放在 lanes/。它和档位正交：lane 选步骤菜单，tier 选产物厚度。lane 只能选路线，不能豁免已经命中的停止点或条件关卡。

PC 冒烟是子 lane / Pack，不是开工三选一。CRUD 命中 E2E Pack 后再读 lanes/pc-e2e-smoke.md。不改 lane，进度写在状态卡「下一步」。不要编造新的 lane 文件名。

强制工作流

适用档位 M/L、跨仓、后端行为、DB、复杂 UI。带全局性质的规则 S/M/L 都适用。档位裁剪只决定产物厚度，不改变这些规则。

① 开场

第一条回复列出本次会碰到的关卡（用停止点表，不要手写一套混合名单），并用 changes/<change-id>/status-card.md 作为用户看得见的状态卡。

② 开工前

  • 读当前变更；source config/runtime_local.sh；确认允许的仓库和路径。路径空不要猜。
  • 区分三标签。未决的假设和问题不得进实现。优先用目标仓样板。
  • 每个业务仓第一次改代码：从 origin/master 或 origin/main 切 harness/<change-id>，记下基线分支和 commit。不在主干改。
  • S/M/L 都跑：confidence-gate.sh、assumption-leak-gate.sh、allowed-paths.sh。
  • M/L 再加：business-code-start-gate.sh（它会校验技术方案已经确认）。S 不要跑这个 gate。
  • 脏仓再加：business-dirty-worktree-gate.sh。参数见 gates/gate_directory.md。

③ 不可豁免

  • 口头「ok / 确认」不能跳过档位需要或条件命中的关卡。命中飞书 PRD 时含飞书同步。
  • 状态卡在阶段变化、阻塞出现或解除、人工确认前后、Tester / Reviewer 返回、验证失效、进入预发、派发子 Agent 时更新。
  • 代码再变，旧结论作废。
  • 主 Agent 可以实施和修复，不得代替 Tester / Reviewer 下结论。

④ 强制项

M/L 默认：全栈技术方案需 CONFIRMED（前端、APP、导出、分析、跨仓行为在范围内时，只有后端方案不算数）；Test Strategy 的测试方案需用户确认；按 skills/skill_directory.md 记录 skill-usage.md，未用写 N/A，并跑 skill-usage-gate.sh。

命中才做：

  • 行为或契约变更：实现前要有 spec 和契约。宣称跑过的检查必须落 evidence。
  • Java 后端行为变更：backend-test-plan.md 或明确 N/A。只编译不够。
  • Swagger 对外 VO：仅当后端仓有活动的 rules/backends/*/manifest.yml profile 时，扫该 profile 的响应根；新增对外 *VO.java 用 @ApiModel 和每字段 @ApiModelProperty。不含导出模型和基础设施 DTO。pre-commit 跑 swagger-model-documentation-gate.sh。
  • 前端 / UI：先判复杂度。PRD UI 要 ui-rule-checklist.md 和 ui-rule-gate.sh。复杂 UI 要可运行页面和 ui-confirmation.md。mapSystem 用 scripts/frontend-dev-server.sh frontend-map-system 9527（Node 14.21.3、产品组登录、临时路由；HomeIndex 重定向即失败）。
  • DB：带 ER 的数据模型、可执行 SQL、规范化检查、自包含注释、字段来源。真实库写入要用户第二次确认。
  • 飞书 PRD：scripts/technical-solution-feishu-sync.sh 同步到飞书子文档，改后重同步，否则技术方案关卡不过。流程图、ER、状态图用白板，不用 Mermaid。
  • 复杂行为或能力边界：写 capability-spec.md / behavior-spec.md，并在 verification-map 里映射。普通 CRUD 写 N/A。

⑤ 环境与就绪

真实 E2E 前填写 environment-readiness.md 并跑 environment-readiness-gate.sh：环境、系统、拓扑、账号来源、数据、写库边界、回滚、设备、阻塞、无可复用凭据。本地后端「可验收」只在 scripts/local-service-lifecycle.sh 的 HEALTH=UP 且 check-web-stack 成功之后才能说。Maven、nohup、端口单独成功都不算。

⑥ 验收与审查

  • 业务代码审查前跑 scripts/code-comment-log-quality.sh。
  • Tester 对照已确认的测试方案，直到 GOAL_ACHIEVED。
  • 提测 / 预发前写测试报告并过 ai-test-report-gate.sh。前置是测试方案已确认，且 Tester 为 GOAL_ACHIEVED。进预发还要建议「允许进入预发」。
  • Reviewer 只读，过 reviewer-gate.sh，high_risk_count: 0。

⑦ 全局禁令

  • 只用 changes/<change-id>/。不建顶层 openspec/。旧产物放 changes/<id>/legacy-openspec/。
  • 永不记录明文密码、token、cookie。
  • CodeGraph 未引入，相关步骤写 N/A。

变更包

一次需求一个目录 changes/<change-id>/，是这次需求的本机工作目录。整包不提交 git（.gitignore 为 /changes/*/）。changes/ 根下的 change-scaffold.sh、status-card.sh、change-whitelist-spec.md 是控制面，要进 git。

建包脚本会做什么

  • 新建目录，并预建 artifacts/，放大文件（截图、录屏、trace、长日志）。
  • 按档位把模版从 templates/ 拷进变更包。
  • 当场生成空的 evidence.md，首行是建包记录。
  • M/L 同时拷 agent-dispatch-plan.md 空壳。

白名单由 changes/change-whitelist-spec.md 定义，gates/change-artifacts-gate.sh 检查有没有名单外的文件。大文件不要摊在包根，也不要放到仓库根的 artifacts/。

状态卡

给人看的单一入口：走到哪、下一步、卡在哪、要不要拍板、子 Agent 在干什么。方案是否 CONFIRMED、环境是否 READY、Tester 是否 GOAL_ACHIEVED，原文在各自 md 里。用户口头确认后，主 Agent 先改对应产物，再改状态卡，再跑 gate。不要只改状态卡就宣称过门。只有主 Agent 能写。子 Agent 不得改。

当前阶段取值：需求理解 / 方案确认 / 允许开工 / 实现中 / AI测试待确认 / 预发待发布 / 已收口。收集脚本 changes/status-card.sh 只读、不裁决，自动推断上限是「允许开工」；「实现中」和「已收口」由主 Agent 在实现开始和收口时手动置位。不要覆盖 Agent Roster。禁止写入 token、cookie、DB password。

这些时候要刷新：有人问「现在到哪了」；阶段切换；阻塞出现或解除；人工确认前后；Tester / Reviewer 返回；审查之后又改了代码；进入预发前；派发、完成或阻塞子 Agent。

证据

evidence.md 是可复查的命令痕迹，不是口头「测过了」。表头：Check | Command / Source | Result | Summary。Result 取 PASS / FAIL / BLOCKED / N/A。每跑一条关键命令就追加，不要覆盖整表，不要等收口再补。长输出只留摘要和 artifacts/ 路径。

它不是验收裁决（那是 Tester 的 test-agent-verification.md），也没有单独的 evidence gate。Reviewer 关卡要求 review.md 引用 evidence。禁止写入 token、cookie、DB password、客户资料、未脱敏 SQL、原始私密 prompt。

受保护行为

  • 不允许把代码提交到 master 或 main。
  • 未经 spec 明确许可，不要改：生产配置、密钥、.env*、部署清单、DB 迁移、Nacos 生产配置、发布脚本，以及 allowed paths 之外的无关模块。
  • 真实 SIT / UAT / 生产库默认只读。真实写入、DDL、任务触发的数据变更或会修改数据的 API，需要目标环境、精确 SQL 或 API、预期行数、回滚或清理计划，以及明确的第二次用户确认。
  • 高危 SQL 全局禁止：DROP DATABASE、DROP TABLE、TRUNCATE、宽范围 DELETE、宽范围 UPDATE，或没有精确范围的写入。
  • 永不在版本化文件、harness 文档、证据或记忆里保存明文 DB 密码、token 或 cookie。
  • 合并前，对变更的业务文件运行 gates/diff-hygiene-gate.sh 和 gates/temp-hardcode-scan.sh。

子 Agent

主 Agent 负责派发。子 Agent 使用新会话，默认看不到主对话。spec、diff 等必读材料写进派发提示的 Read inputs，由子 Agent 自己读磁盘。控制面默认只允许主 Agent 写。

  • Explorer（subagents/explorer_agent.md）：只读查证，按三标签把材料交回主 Agent。
  • Reviewer（subagents/reviewer_agent.md）：只写 review.md。high_risk_count 为 0 才建议进人审。
  • Test Strategy（subagents/test_strategy_agent.md）：写 ai-test-plan.md，不写业务代码。
  • Tester（subagents/tester_agent.md）：对照已确认测试方案验收，维护 test-agent-verification.md。
  • Backend / Frontend / Mobile：候选。契约、允许路径、隔离 worktree 齐了才派。前端只读契约。

每个子 Agent 提示词以 Agent Label: <change-id> / <role> / <scope> 开头，并声明写入范围、禁止路径、要求产出、是否只读。最终回复以 <role>: DONE|PASS|BLOCKED|NEEDS_CONTEXT 开头。主 Agent 在状态卡 Agent Roster 里记录同样的标签和状态。细则见 subagents/dispatch_subagent.md。

完成定义

  • spec、plan、契约与档位 M/L 的技术方案一致。
  • 没有未解决的假设或问题进入代码。需要测试方案时，ai-test-plan.md 已确认。
  • 做过 E2E 的，环境就绪写清楚。
  • Tester 已确认 GOAL_ACHIEVED，或记录 BLOCKED 并升级给用户。
  • Reviewer 产出已通过 gates/reviewer-gate.sh。
  • 残余风险和回滚已记录。
