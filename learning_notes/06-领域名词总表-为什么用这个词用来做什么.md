怎么读「类别」：

| 类别 | 意思 |
|---|---|
| 总概念 | 整套东西是什么，不是某个文件 |
| 规则（Guide） | 写给 Agent 看的说明，靠读，不自动拦 |
| 文件 / 工件 | 一次工作里要落下的 Markdown 等 |
| 流程 | 先做什么后做什么 |
| **限制 / 关卡** | 不满足就失败，不该进入下一步 |
| 角色 | 谁可以写、谁只能看 |
| 接线 | Cursor 等 runtime 怎么接到你的脚本 |
| 评测 | 用来衡量 harness 自己，不是衡量业务需求 |

## 1. 总概念：这套东西是什么

### harness

- **为什么用这个词：** 马具、安全带：不是马本身，是套在外面让力用对地方的装置。2026 前后 Fowler《Harness engineering》、OpenAI Harness Engineering 把 coding agent 说成 **Model + Harness**。
- **用来做什么：** 统称你在模型外面加的东西：入口文档、模板、gate、hook、状态卡。
- **不是：** Cursor 那个可执行内核。那叫 runtime。
- **限制还是流程：** 都不是，是总称。
- **标本：** 整个 `learning_objectives` 就是控制面 harness。
- **自建：** 说话时保留「harness」；仓库名不必带这个词。

### runtime

- **为什么：** run-time，程序跑起来的那一层。
- **用来做什么：** 提供 agent loop、读文件、跑 shell、权限、sandbox。
- **和 harness 的关系：** runtime 负责「能跑」；你的 harness 负责「在边界里跑」。
- **自建 v0：** 先只挂 Cursor。

### control plane（控制面）

- **为什么：** 网络/K8s：控制面发策略，数据面转发流量。标本用来比喻：规矩仓 vs 业务仓。
- **用来做什么：** 禁止把业务代码复制进 harness 仓；用 registry + 本地路径变量指向业务仓。
- **限制：** 控制面自己的 git 里不放 Java/Vue 实现。
- **自建：** 对人只说「控制面」。

### Context engineering（上下文工程）

- **为什么：** Karpathy 等强调：现在瓶颈是喂给模型的上下文，不是一句 prompt 文案。
- **用来做什么：** 决定读哪些文件、注入多长、历史 change 不要全量灌进窗口。
- **和渐进披露：** 同一件事的两面——入口短、按需打开。

## 2. 规则层：告诉 Agent 怎么做（不自动拦截）

### AGENTS.md

- **为什么这个文件名：** Codex / Cursor / 社区 `agents.md` 约定根目录找它。改成 `规则.md` 工具可能不读。
- **用来做什么：** Agent 的 README。只放硬规矩和索引。
- **限制：** 它本身**不能**拦住 `git commit`。限制要靠 gate/hook。
- **流程位置：** 第 1 步就写。之后每加一类能力，只在这里加一行指针，不把正文贴满。
- **自建：** 文件名必须英文这个。

### skill / SKILL.md

- **为什么：** Anthropic 把「一项可复用工作」叫 skill；Cursor 同样用 `SKILL.md`。
- **用来做什么：** 例如 Reviewer：何时启动、只读、输出 `review.md`、禁止改业务代码。
- **和 AGENTS 的差别：** AGENTS 是总目录；skill 是某一角色的完整说明书，用到再读（渐进披露）。
- **限制：** 纯文字纪律，模型可能不调。要用 eval 或 hook 补。
- **自建：** 目录 `skills/reviewer/SKILL.md` 这个形态留着。

### Guides（引导）

- **为什么：** Fowler 把 harness 拆成 Guides（事前）和 Sensors（事后）。
- **用来做什么：** 所有「请按这个做」的 Markdown：AGENTS、docs、rules、templates、lanes、skills。
- **限制：** 没有。Guide 失败不会 exit 1。
- **自建：** 不要把 Guides 写进给你看的 AGENTS；写「规则」。

### baseline（基线）

- **为什么：** 「未改之前仓库的常态」。
- **用来做什么：** 这个前端列表页用哪些 class、API 从哪一层走。给 Agent 仿写，减少「能跑但不像这个仓」。
- **流程：** 改某个仓之前读对应 baseline。v0 可以还没有。
- **标本：** `docs/baseline/frontend-map-system.md` 这类。自建按你的仓写，不要抄 SFA。

### progressive disclosure（渐进披露）

- **为什么：** 界面设计用语：先给少，点开再给多。OpenAI 用来要求 AGENTS 像目录。
- **用来做什么：** 防止一次塞进 38 个 gate 的说明把模型塞笨。
- **流程：** 入口 → 当前 change → 命中的 lane/skill → 才读细则。

## 3. 一次工作：流程 + 文件

### change / 变更包 / `changes/<id>/`

- **为什么：** 变更管理：一次有边界的改动一个号。
- **用来做什么：** 聊天不是事实源。这次的 spec、状态、证据都在这个文件夹。
- **流程：** 新需求先起一个 id，再复制模板进去。
- **限制：** 标本规定新工作不要另起顶层 `openspec/`。
- **自建：** 可留 `changes/` 这个英文目录。

### artifact（工件）

- **为什么：** CI 说 build artifacts；这里指定制的那几份 Markdown。
- **用来做什么：** 轻量工作强制 3 个文件，重的才加方案/测试，避免每次临时起名。
- **标本档位：** 轻 = spec + status + evidence。

### spec.md

- **为什么：** specification，这次做成什么样。
- **用来做什么：** 目标、范围内外、三标签、allowed_paths。
- **限制：** 单独存在还不限制任何事，要配 gate。
- **流程：** 变更包里第一份实质内容（学习路径第 2 步）。

### `[FACT]` / `[ASSUMP]` / `[QUESTION]`

- **为什么用英文方括号：** 不是行业标准，是标本为了 **grep / gate** 做的稳定标记。
- **用来做什么：**
  - FACT：有出处才写（人、PRD、代码、契约）
  - ASSUMP：猜测；**限制：确认前不准进实现**
  - QUESTION：必须问人；**限制：没答就停**
- **流程：** 写 spec 时强制三块都出现（没有假设就写 `None`）。
- **自建：** 建议保留这套记号，对人说话用中文。

### status.md（标本：harness-status.md）

- **为什么：** 给人看的仪表，不替代 spec。
- **用来做什么：** 当前阶段、下一步、YES/NO、阻塞、待你确认。
- **流程：** 阶段变了就改；不要等收尾才写。
- **限制：** 它不拦截。拦截看上面的 Gate 状态是不是红的。

### evidence.md

- **为什么：** 完成必须可复查。superpowers 叫 evidence before claims。
- **用来做什么：** 命令、退出码、摘要。禁止密码。
- **限制：** 没有 evidence 就不该宣称「测过了」。v0 可先习惯手记，以后再对这个文件加 gate。
- **流程：** 每跑一次关键脚本就追加。

### review.md

- **为什么：** 审查产出物的常规名。
- **用来做什么：** HIGH/MEDIUM、路径、是否建议进入人审。
- **限制：** Reviewer 只写这个（及约定文件），不改业务代码。
- **流程：** 实现和常规验证之后、人审/PR 之前。

### lane（任务路线）

- **为什么：** 泳道：不同类型不同路径，避免一条巨流程。
- **用来做什么：** `lanes/tiny.md` 列出编号步骤：复制 spec → 跑 spec-gate → …
- **限制：** lane 是清单，不是脚本。不跑 lane 不会自动失败。
- **流程：** AGENTS 里写「小改走 tiny」。

### Optional Pack（附加流程）

- **为什么：** 标本怕 CRUD 也背上 UI/E2E/飞书。Pack = 默认不装的扩展包。
- **用来做什么：** 命中条件才追加（复杂 UI、真 E2E…）。
- **限制：** 未命中应在 plan 里写 N/A，不是漏做。
- **自建：** v0 没有 pack。名字改成「附加流程」。

### Tier / 轻中重

- **为什么：** 用尺码表示「这次多重」，决定强制哪些工件。
- **用来做什么：** 轻：三件套；中/重才加技术方案、独立验收。
- **限制：** 标本来了以后用 `change-artifacts-gate` 卡文件名；v0 靠人遵守 tiny。

### stop point（停止点）

- **为什么：** 强调「停」，不是「尽量注意」。
- **用来做什么：** 三类——业务口径不清、工程边界不安全、验证证据不足。
- **流程：** 用户说「ok / 开始开发」只推进到**下一个已满足的关卡**，不豁免停止点。
- **限制：** 这是流程纪律；落地要靠 gate + 状态卡 + 人。

### contract（契约）

- **为什么：** 接口合同，前后端共同遵守。
- **用来做什么：** endpoint、字段、错误码、空态。标本常要 v0.1 才允许前后端并行。
- **流程：** 在技术方案/写代码前冻结。v0 tiny 可以没有。

## 4. 限制 / 关卡：不满足就不能往下

### gate（关卡）

- **为什么用这个单词：** CI/CD 的 quality gate、merge gate：过不了门就不能进下一环境。不是标发明。
- **用来做什么：** 一段**确定性**脚本。读文件、路径、字段。`exit 0` 过，非 0 不过。错误里带 FIX，给 Agent 自己修。
- **限制什么：** 「能否进入下一动作」——例如能否开始改业务代码、能否宣称审查完成。
- **不限制什么：** 代码好不好看、方案是否合理（那是 Reviewer / 人）。
- **和规则的差别：** `AGENTS.md` 写「请先确认」是 Guide；`spec-gate.sh` 扫 QUESTION 是 gate。
- **和 hook 的差别：** gate 是「被调用时跑」；hook 是「事件到了自动去调 gate」。
- **标本例子：** `confidence-gate.sh`、`allowed-paths.sh`、`reviewer-gate.sh`。
- **自建：** 词留着；第一个脚本建议叫 `spec-gate.sh`。

### fail-closed

- **为什么：** 安全工程：失败时选择关闭/拒绝，而不是放行。
- **用来做什么：** spec 找不到 → 失败；环境变量没设 → 不要「跳过检查当通过」。
- **标本踩过的坑：** 没设 `SFA_CHANGE_SPEC` 时 afterFileEdit 直接放行，变成 fail-open。

### Sensors（传感器）

- **为什么：** Fowler：执行后给反向压力，让 Agent 自我纠正。Thoughtworks 说自定义 linter 的报错是写给 LLM 读的。
- **用来做什么：** 所有检查：gate、compile、lint、测试、推断性审查。
- **分层：** 先确定性（脚本），再推断性（Reviewer）。
- **自建：** AGENTS 里写「检查脚本」。

### Computational vs Inferential

- **为什么：** Fowler：能算清的用脚本（快、便宜、可重复）；要判断的用模型（慢、贵、会漂）。
- **用来做什么：** 决定「这事该写成 gate 还是交给 Reviewer」。路径是否在白名单 = 计算；架构漂不漂 = 推断。

### allowed_paths / forbidden / protected

- **为什么：** 白名单 / 黑名单 / 受保护资源，权限模型里的老词。
- **用来做什么：** 限制**手伸到哪**。gate 比对「将要改的文件」和 spec 里的名单。
- **限制：** 生产配置、`.env*`、migration 默认禁止，除非 `approved_protected_paths` 且人二次确认。
- **流程：** 写进 spec → `allowed-paths.sh spec 文件1 文件2`。
- **自建：** YAML key 留英文。

### Constraints（约束层）

- **为什么：** 五层模型第 2 层：不是「怎么做」，是「什么不能碰、何时必须停」。
- **用来做什么：** 把 allowed_paths、protected、hook 权限和「请小心」区分开。
- **限制：** 这一层才应该 fail-closed。

### confidence-gate（标本名）→ 自建 spec-gate

- **为什么标本叫 confidence：** 他们痛点是「没 95% 把握的事写进代码」。名字像口号。
- **实际做什么：** 检查 spec 里有没有三标签、阻塞 QUESTION 清没清。
- **限制：** 问题没答完，按理不该开工。标本里它常是**拉式**（要人/Agent 去跑）。
- **流程：** 学习路径第 3 步，紧跟 spec。

### assumption-leak-gate

- **为什么：** leak = 泄漏：假设从 spec 漏进 `.java`/`.vue`。
- **用来做什么：** 扫**实现文件**，不是再扫一遍 spec。
- **限制：** 和 spec-gate 成对——文档关 + 代码关。
- **流程：** 准备改代码或提交前。

### code-start（开工检查）

- **为什么：** 「业务代码第一次编辑」这个时刻。
- **用来做什么：** 把方案确认、路径、分支不是 main 等捆成一个总检。
- **限制：** 标本设计上未过此门不准改业务仓；实际常没 hook 自动跑。
- **流程：** v0 可先拆成 spec-gate + allowed-paths；总检是加厚项。
- **对人：** 叫开工检查。

### reviewer-gate

- **用来做什么：** 检查 `review.md` 是否存在、HIGH 是否为 0 等**合同字段**。
- **限制：** 不判断代码质量本身；判断「审查工件合不合格」。
- **流程：** 人审前。

## 5. 角色

### Orchestrator / 主 Agent

- **为什么：** 编排者：自己少动手、让别人按序干活。标本规定**只有它可写控制面**。
- **用来做什么：** 更新状态卡、集成、在允许路径内实现和修复。
- **限制：** 不能替代独立验收和只读审查的裁决；用户说 ok 不能跳过关卡。
- **自建 v0：** 叫主 Agent，一个人会话即可。

### Reviewer

- **为什么：** 审查者。superpowers 强调不信任 implementer 报告。
- **用来做什么：** 读 spec、diff、evidence，写 review.md。
- **限制：** **只读**业务代码；禁止边审边改。
- **流程：** 验证之后、PR 之前。最好换上下文（子 Agent）。

### Test Agent / 验收

- **为什么：** 标本怕「实现的自己说测过了」。
- **用来做什么：** 对照已确认的测试计划复测，直到 PASS 或 BLOCKED。
- **限制：** 不能宣称「功能实现完成」；只能验收。
- **标本状态字：** `GOAL_ACHIEVED` — 自建改 `PASS`。
- **v0：** 可先只有 Reviewer + 人；没有独立 Test Agent。

### subagent

- **为什么：** 子会话、独立上下文窗口。Cursor 工具就叫这个。
- **用来做什么：** 探索只读、审查只读、一块实现任务。
- **限制：** 要写清只读还是可写、禁止路径、输出文件。标本默认 Explorer/Reviewer 只读；实现 agent 要隔离 worktree。

## 6. 接线：runtime 怎么接到检查

### hook

- **为什么：** 钩子：挂在「即将执行 shell / 已经改完文件」这类事件上。
- **用来做什么：** **推式**调用你的脚本，不靠模型想起来。
- **限制能力（必须分清）：**
  - **之前**（beforeShell / PreToolUse）：能挡住 `git commit`、危险命令。
  - **之后**（afterFileEdit / PostToolUse）：文件已在磁盘上，**不能撤销**，只能报警、拦下一步。
- **自建：** 配置文件名必须按 Cursor 的 `hooks.json`；逻辑仍放 `scripts/`。

### adapter（薄适配）

- **为什么：** 适配器：Cursor 事件名和 Codex 不一样，不要各写一套检查逻辑。
- **用来做什么：** `hooks/cursor-before-shell-execution.sh` 只转发到 `harness-sensor-runner.sh`。
- **限制：** 标本写明不要改 runner 除非另走方案；学习时理解「接线薄、逻辑一处」。

### 拉式 vs 推式

- **拉式：** Agent 必须执行 `scripts/spec-gate.sh`。忘了就没限制。
- **推式：** commit 前 hook 强制跑同一脚本。忘了也拦得住版本化。
- **标本诊断：** 关键安全门是拉式，所以「没确认方案也能改代码」。
- **流程：** 先有 gate（能跑），再接线（自动跑）。学习路径第 3 步 gate，第 11 步 hook。

### worktree

- **为什么：** Git 原词：同一仓库多个工作目录。
- **用来做什么：** 两个实现 Agent 不在同一脏工作区互踩。
- **限制：** 标本对实现类 subagent 要求隔离；v0 单人可先不用。

## 7. 评测（v0 不做，词要认识）

### eval

- **为什么：** evaluation，模型/agent 圈通用。
- **用来做什么：** 改 AGENTS/skill 之后，行为还守不守规则。脚本单测 ≠ 行为 eval。
- **不是：** 用来给业务需求打分当上线依据。
- **以后：** superpowers 的 drill、ECC 的 skill-comply。文件名/术语保留 eval。
